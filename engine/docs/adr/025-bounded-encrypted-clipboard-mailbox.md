# ADR-025：采用有界端到端加密剪贴板邮箱与统一事件身份

- **状态**：已采纳并实施
- **日期**：2026-08-23
- **修订**：架构总览“离线投递恢复”中“不建立队列”的绝对表述，以及产品仓中禁止任何
  store-and-forward 的旧约束
- **相关文档**：`docs/specs/027-fullmesh-clipboard-event-and-mailbox.md`、
  `docs/architecture/architecture-bible.md`

## 背景

现有 Iroh/QUIC 会优先使用可达直连并在需要时使用盲中继，但发送瞬间目标设备暂停、移动设备被系统挂起或
双方网络切换时，单次在线传输仍可能失败。仅在对端重新上线时补送本机最新一条内容，无法覆盖短时间错峰，
也无法让 direct 与 relay 对同一份小负载竞速。

FullMesh 交付规范要求所有平台共用稳定事件身份、持久重放窗口和短 TTL 密文邮箱。该要求高于旧产品仓的
“任何 store-and-forward 都禁止”约束，但不允许把剪贴板同步改造成无限消息队列或中心云历史。

## 决策

### 一个事件身份贯穿所有传输

Engine 为每次投递建立 `ClipboardEventEnvelope`。`event_id` 使用 UUIDv7；`origin_sequence` 由本地数据库按
设备原子分配并跨重启单调递增。direct、Iroh relay 和密文邮箱携带相同的 `event_id`、内容摘要、目标与 TTL，
接收端由一个持久事件窗口决定赢家，宿主不得重建另一套协议或去重规则。

### 邮箱严格有界

邮箱只用于非文件小负载的机会型投递。默认 TTL 为五分钟，协议允许的最大 TTL 为二十四小时；服务端同时
限制单消息大小、单邮箱数量、总容量和请求速率。租约确认后删除，过期自动清理，重复上传同一事件幂等。
文件和目录继续使用现有流式、可恢复的 Iroh Blob 路径，不进入邮箱。

邮箱不是历史同步：不会扫描或上传旧历史，不向后来加入的设备补发，不无限重试，也不承诺最终一致。现有
“设备重新在线时最多补送本机最新一条未送达内容”的规则仍保留；短 TTL 邮箱只是同一当前事件的另一条
受限传输路径。

### 服务端只能处理密文与最小路由资料

客户端先用 Space 的传输密钥封装完整邮箱帧，再进行外层 AEAD 加密。服务端没有 MasterKey，看不到事件正文、
MIME 详情、文件名、路径或原始 `event_id`。邮箱编号与事件键由客户端用凭据进行 HMAC 派生；服务端只保存
密文、派生路由键、到期时间、长度、摘要和租约状态。

TLS 终结层在认证请求时会接触 bearer token，因此部署方可以观察认证流量；服务不得持久保存或记录 token，
生产部署必须使用 TLS，并采用每 Space 独立的可轮换凭据。该元数据边界必须在威胁模型中明确披露。

### 重放与冲突边界

接收端在内容提交前检查持久 `event_id` 窗口；窗口最多保留 10,000 条，最长二十四小时，并在历史条目删除后
继续保留 tombstone。事件写入与 tombstone 写入处于同一 SQLite 事务。direct 与邮箱同时到达时只有一个路径
提交，另一条得到重复终态并确认删除邮箱消息。

内容回环继续使用 `content_hash`、系统剪贴板自写账本和活动剪贴板 LWW 寄存器。`event_id` 处理同一投递的
多路径重复，`content_hash` 处理独立事件携带相同内容；两者不互相替代。过期、目标不符、跳数超限、身份或
摘要不一致的信封均拒绝，不得写系统剪贴板。

### 平台和在线状态

平台宿主只配置邮箱服务地址与凭据，并消费 Engine 的统一结果。移动端后台受限时仍是同一身份节点，但不能
被描述为稳定在线转发节点。Presence 分开表达已配对、最近可达、实时连接、后台受限和离线；机会型转发不
参与消息正确性前提。

## 取代范围

本 ADR 只取代以下旧约束：

1. “任何 store-and-forward 邮箱都禁止”；
2. “投递只能在发送瞬间在线或等设备上线后补送最新一条”的排他性表述；
3. “服务端绝不保存任何剪贴板相关字节”的绝对表述，改为“只保存有界短 TTL 的端到端密文”。

以下边界继续有效：无账号体系、无服务端 MasterKey、无明文业务负载、无无限队列、无完整历史云同步、无
最终一致承诺、无平台协议分叉、文件仍走流式传输、日志不记录内容或秘密。

## 结果

- 短时离线和网络切换不再要求发送方与接收方严格同时在线。
- 小负载可让实时路径与邮箱竞速，以持久 `event_id` 去重。
- 部署方承担密文容量、过期清理、认证和元数据保护责任。
- 产品文档、诊断页和隐私说明必须区分 Iroh blind relay 与短 TTL 密文邮箱。

## 未采用的方案

### 服务端解密或按 MIME 选择路由

这会使服务持有业务密钥或内容分类，破坏端到端边界，因此拒绝。

### 无限离线队列或完整历史同步

这会改变产品语义、扩大元数据和存储风险，也不符合个人设备间剪贴板的当前范围，因此拒绝。

### 由各平台分别实现邮箱协议

这会复制事件、加密、重放和兼容规则，违反统一 Engine 边界，因此拒绝。
